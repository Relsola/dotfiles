# 编程风格

## 编程绝对原则

1. 用 C++ 编写代码 C 风格代码，保证有接近 C 的编译速度获得一些语言层面的改良。
    > 禁止自行引入第三方库依赖
2. 保持高性能编码风格，牺牲性能换取的抽象设计必须要有明确的理由以及明显的收益。
    > 局部缓存性优于抽象优雅，数据布局决定后续性能优化上限
    > 使用编译器内建函数 (`intrinsic`)
3. 出现抽象泄漏、依赖成环、没有单一真相来源、代码修改复杂度爆炸等情况必须优化架构和实现。

## 可以使用的 C++ 特性

这些特性几乎不增加编译时间，也不会带来心智负担，但能直接增强开发体验。

1. 函数重载和默认参数: 可以有效减少冗余，提高可读性。
2. `constexpr` 和 `consteval`: 代替大部分宏函数和常量，类型安全，且可调试，但无法代替元编程和减少代码重复的宏。
3. `lambda`: 一次性局部回调。
4. `auto`: 类型推导。
5. `nullptr`: 语义优化

## 谨慎使用的 C++ 特性

这些特性有用，但可能增加复杂度或编译时间。

1. 简单模板: 解决 C 中没有泛型的问题。
2. 运算符重载: 由于会产生隐式行为，只在数学计算时使用。
3. 标记和属性: 给编译器一些可用确定的信息。

## 绝对禁用的 C++ 特性

这些特性是复杂度和编译时间的主要来源。

1. 异常和RTTI: 运行时类型信息，增加了编译时间和可执行文件大小，异常我会显式处理。
2. 重型STL: 复杂度和编译时间的主要来源，隐式行为过多，难以调试。
3. 智能指针和引用: 显示管理内存，且使用 C 中的指针。
4. 虚函数和继承: 不使用面向对象编程。
5. 模板元编程: 复杂度和编译时间的主要来源，严重增加心智负担，且难以调试。

## 使用基本类型别名和 static 关键字别名

别名定义如下

```cpp
#include <stdint.h>

#define internal        static
#define local_persist   static
#define global_variable static

using i8  = int8_t;
using i16 = int16_t;
using i32 = int32_t;
using i64 = int64_t;

using u8  = uint8_t;
using u16 = uint16_t;
using u32 = uint32_t;
using u64 = uint64_t;

using f32 = float;
using f64 = double;
```

注意：没有精确语义的地方，整数使用 `int`，浮点数使用 `f32` 

## 命名风格

- 函数命名如： `create_app`  一般为正常小写单词下划线分割命名。

- 变量命名如： `box_id`  一般为正常小写单词下划线分割命名。

- 结构体命名如： `struct AppInfo {}`  一般为首字母大写驼峰命名。

- 中间体命名前面加上 `__` 如: `__Defer`

## Windows 系统级编程

- 使用 `Unicode` 版本 Windows API。

- 没有特殊原因使用原生 API， 如使用 `CreateFileW` 打开文件而不是标准库封装的 `fopen_s`。

- 使用当前支持的稳定新 API 而不是过时的旧模板代码 API。

## 编程习惯

1. if 必须要有括号包裹作用域，且除了连续 if 判断场景括号可以写在一行，其它必须换行。

```cpp
// 1. 普通场景
if (cond) {
    // ...
}

// 2. 连续判断且语句很少可以改为单行，但需要对齐
if (cond1) { }
if (cond2) { }
if (cond3) { }

if (cond1)     { }
else if(cond2) { }
else if(cond3) { }
else           { }
```

2. 常量使用 `constexpr` 定义。

3. 不要过多考虑极端错误边界情况（如内存分配失败等极端情况）做太多错误处理逻辑而导致迭代代码冗余。

4. 检查约定（如特殊默认约定的参数等）、符合显式规律的地方使用 `assert` 断言。

5. 一般情况不使用结构体函数（隐式this传参）而是使用显式声明函数传参。

6. 如果一个函数只在一个地方被调用，直接将其内联到调用处，而不是为了模块化而单独抽离出来。

7. 数据结构通常直接使用数组，并在合适的适合使用 `AoSoA (Array of Structures of Arrays)`

8. 文件内类型和高频冲突命名使用 `namespec` 隔离，一般直接使用语义化命名区分。
